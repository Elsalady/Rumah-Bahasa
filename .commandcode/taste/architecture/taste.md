# architecture
- For "Tentang Rumah Bahasa" section on the homepage/dashboard: use hardcoded text in code files, not database-driven (the Profil model is only for the /profil page managed via admin). Confidence: 0.75
- Convert timestamps to WIB at the display layer (`->timezone('Asia/Jakarta')` in views/controllers) rather than changing Laravel's global `config('app.timezone')` from UTC — stored data stays in UTC and only rendering converts it, avoiding shifting already-stored historical data. Apply the same conversion consistently across admin views, member-facing views, and export CSV output. Confidence: 0.75
- Prefer combining related content into existing pages/sections rather than creating new standalone pages — when given the option between a separate page vs. a subsection, the user consistently chooses consolidation to keep the site structure lean. When an existing feature/form already exists (e.g., the public "hubungi kami" contact message box), reuse it via deep-link instead of building a new page — the user explicitly rejected a newly-created member-internal messaging page in favor of linking to the existing website form. Confidence: 0.75
- When multiple conceptually-related content items (e.g., "Visi" and "Misi") are displayed together in one unified card and share a single "Lihat Selengkapnya" detail/show link, store them as ONE database record with structured/combined content (e.g., newline-separated sections with embedded labels) rather than as separate records. Separate records would cause the detail/show page to only display one item, breaking the full combined view the user expects. Confidence: 0.78
- Class schedule quota should auto-calculate remaining capacity based on confirmed registrations (sisa kuota = total kuota from all schedules - jumlah pendaftar confirmed) rather than requiring manual updates by admin. Confidence: 0.75
- Filter which admin/system operations generate notifications for members — only member-facing content changes (e.g., new/updated programs, class schedules) should trigger member notifications; internal admin housekeeping operations (e.g., periodic schedule resets) should NOT generate member notifications. Confidence: 0.70
- When admin creates, updates, or deletes member-facing resources (e.g., jadwal kelas), auto-create notifications for all approved members so they stay informed of changes without manual communication. Confidence: 0.82
- Never overwrite existing/production database content by re-running seeders — inspect the DB first, and if it contains original/real data, insert only the missing records directly (e.g., via tinker) to preserve the real content. Confidence: 0.88
- When seeding/demoing data, reference real existing assets (e.g., actual image files already present in storage/public) rather than invented placeholder filenames that don't exist — so pages render with real content immediately. Confidence: 0.82
- When the database is missing a table that should exist (e.g., a Laravel default table like password_reset_tokens absent due to an incomplete/legacy migration), fix it by creating a new additive migration and running `migrate --force` — never run migrate:fresh or re-run old migrations to repair schema gaps, since that would destroy existing real data. Confidence: 0.8
- Prefer Laravel's built-in facilities (Password reset broker, Mailable classes, standard auth routes) over hand-rolled custom implementations for standard framework features. Confidence: 0.6
- Environment-specific behavior should be gated on the environment rather than applied globally — e.g., the AppServiceProvider fallback that overrides the root URL with the request host is useful for LAN development but must only run in `local`/non-production environments so it doesn't override the real `APP_URL` in production (which would break links in emails/sitemaps when the site is accessed via IP). Confidence: 0.85
- Class schedules are managed on a per-week basis: the admin sets schedules for the current week (each jadwal linked to a program via layanan_id), and old weekly schedules are automatically reset/deleted (scheduled reset command) — plus all queries filter to the current week (Senin–Minggu) so stale history never shows even before the reset runs. Confidence: 0.85
- Members can only register for a program when the admin has published at least one active schedule for the current week — the "Daftar" button must be disabled when no schedule exists, and the backend (PendaftaranController) must also block registration as defense-in-depth, not just UI hiding. Confidence: 0.85
- Avoid member-facing features that require technical configuration by non-technical admins (e.g., SMTP/email setup): the user asked to make the forgot-password flow "automatic so the admin doesn't get confused" and chose to remove the entire email-based feature rather than have admins configure SMTP — password resets are now done manually by the admin (artisan command) and communicated via WhatsApp, a channel the project already uses. Prefer flows that work out-of-the-box/offline over feature completeness. Confidence: 0.75
