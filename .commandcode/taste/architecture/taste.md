# architecture
- For "Tentang Rumah Bahasa" section on the homepage/dashboard: use hardcoded text in code files, not database-driven (the Profil model is only for the /profil page managed via admin). Confidence: 0.75
- Convert timestamps to WIB at the display layer (`->timezone('Asia/Jakarta')` in views/controllers) rather than changing Laravel's global `config('app.timezone')` from UTC — stored data stays in UTC and only rendering converts it, avoiding shifting already-stored historical data. Apply the same conversion consistently across admin views, member-facing views, export CSV output, AND data mapped in controllers before JSON serialization for JS-rendered tables — raw ISO/UTC strings must not leak into the frontend. Confidence: 0.8
- Prefer combining related content into existing pages/sections rather than creating new standalone pages — when given the option between a separate page vs. a subsection, the user consistently chooses consolidation to keep the site structure lean. When an existing feature/form already exists (e.g., the public "hubungi kami" contact message box), reuse it via deep-link instead of building a new page — the user explicitly rejected a newly-created member-internal messaging page in favor of linking to the existing website form. Confidence: 0.75
- When multiple conceptually-related content items (e.g., "Visi" and "Misi") are displayed together in one unified card and share a single "Lihat Selengkapnya" detail/show link, store them as ONE database record with structured/combined content (e.g., newline-separated sections with embedded labels) rather than as separate records. Separate records would cause the detail/show page to only display one item, breaking the full combined view the user expects. Confidence: 0.78
- Class schedule quota should auto-calculate remaining capacity based on confirmed registrations (sisa kuota = total kuota from all schedules - jumlah pendaftar confirmed) rather than requiring manual updates by admin. Confidence: 0.75
- Admin-managed content should use a single source of truth shared across all display areas: when the admin creates a program (in the `layanan` table), it must automatically appear everywhere it's shown — the homepage "Lingkup Pelatihan" section AND the member dashboard "Lihat Program" list — with no manual duplication or per-page sync. The user explicitly asked that a new program added in admin "otomatis terupdate" to both places; the assistant verified this works because both views query the same `layanan` table (filtered by `is_active = true`) rather than separate lists. Confidence: 0.8
- Filter which admin/system operations generate notifications for members — only member-facing content changes (e.g., new/updated programs, class schedules) should trigger member notifications; internal admin housekeeping operations (e.g., periodic schedule resets) should NOT generate member notifications. Confidence: 0.70
- When admin creates, updates, or deletes member-facing resources (e.g., jadwal kelas), auto-create notifications for ALL approved members (not just members enrolled in the affected program) so everyone stays informed — when asked to choose between broadcasting to all members vs. only program-enrolled members, the user explicitly picked "Semua member", and the notification helper was changed to drop per-program targeting (and its now-unused imports) in favor of a blanket broadcast to every approved member. Confidence: 0.92
- When an admin changes a member's account status (approve/reject) and writes a note (catatan), the note must be surfaced to the member — create an in-app notification carrying the admin's note (title reflecting the outcome, e.g., '✅ Akun Kamu Disetujui' / '❌ Akun Kamu Ditolak') rather than only persisting the note in the DB; the user asked that the note appear "di bagian notifikasi atau bagian atas dashboard member". Confidence: 0.85
- Never overwrite existing/production database content by re-running seeders — inspect the DB first, and if it contains original/real data, insert only the missing records directly (e.g., via tinker) to preserve the real content. Confidence: 0.88
- When seeding/demoing data, reference real existing assets (e.g., actual image files already present in storage/public) rather than invented placeholder filenames that don't exist — so pages render with real content immediately. Confidence: 0.82
- When the database is missing a table that should exist (e.g., a Laravel default table like password_reset_tokens absent due to an incomplete/legacy migration), fix it by creating a new additive migration and running `migrate --force` — never run migrate:fresh or re-run old migrations to repair schema gaps, since that would destroy existing real data. Confidence: 0.8
- Prefer Laravel's built-in facilities (Password reset broker, Mailable classes, standard auth routes) over hand-rolled custom implementations for standard framework features. Confidence: 0.6
- Environment-specific behavior should be gated on the environment rather than applied globally — e.g., the AppServiceProvider fallback that overrides the root URL with the request host is useful for LAN development but must only run in `local`/non-production environments so it doesn't override the real `APP_URL` in production (which would break links in emails/sitemaps when the site is accessed via IP). Confidence: 0.85
- Class schedules are managed on a per-week basis: the admin sets schedules for the current week (each jadwal linked to a program via layanan_id), and schedules whose date has already passed are AUTOMATICALLY DELETED (not just hidden) so the admin must re-set them for the following week — the user gave an explicit scenario: schedules set Mon–Sat on Monday must show Mon/Tue as deleted/empty by Wednesday while Wed–Sat remain. The deletion is implemented as lazy cleanup in `Admin\ProgramController@kelola` (`whereDate('tanggal','<',Carbon::today())->delete()` whenever the admin opens the schedule page) rather than a cron job; schedules with a NULL tanggal (legacy pre-tanggal data) are preserved unless the user asks to delete those too. Plus all queries filter to the current week (Senin–Minggu) so stale history never shows even before the cleanup runs. Confidence: 0.9
- Members can only register for a program when the admin has published at least one active schedule for the current week — the "Daftar" button must be disabled when no schedule exists, and the backend (PendaftaranController) must also block registration as defense-in-depth, not just UI hiding. Confidence: 0.85
- Class schedules whose date has already passed must automatically become unavailable for member registration — the schedule should disappear from the member-facing schedule list and the "Pilih Jadwal Kelas" dropdown (filter `$jadwalProgram` to dates >= today), AND the backend (PendaftaranController@store) must reject registration with an error as defense-in-depth, so a member cannot register for a class that already happened (user scenario: registering on Thursday for a Monday class must be impossible). Schedules with a missing date (legacy data from before the tanggal feature) may remain visible for backward compatibility unless the user asks to treat them as expired too. Confidence: 0.8
- Avoid member-facing features that require technical configuration by non-technical admins (e.g., SMTP/email setup): the user asked to make the forgot-password flow "automatic so the admin doesn't get confused" and chose to remove the entire email-based feature rather than have admins configure SMTP — password resets are now done manually by the admin (artisan command) and communicated via WhatsApp, a channel the project already uses. Prefer flows that work out-of-the-box/offline over feature completeness. Confidence: 0.75
- Guest-facing registration CTAs on public pages (e.g., the "Daftar Sekarang" button on program detail pages reached via "Lihat Detail" in Lingkup Pelatihan) should be login-gated: clicking it must route guests to the login page (not the register page), since enrollment happens inside the member area; for already-authenticated users the same button should route to the member program area. Confidence: 0.75
- ~~Prefers keeping the member registration flow simple (register directly per program, no schedule-selection step)~~ — SUPERSEDED: this applied only while registrations were per-program and admin reports grouped them at the display level via name matching. When the user later asked for type-specific enrollment behavior (tematik auto-expires weekly vs tentative lasts a semester), the registration flow was extended to capture the class type (jenis: tematik/tentative) and the chosen schedule (jadwal_id) — a form choice between the two types (with explanations) plus a schedule dropdown — backed by a migration adding jenis/mode/jadwal_id to pendaftaran, so per-type expiry and per-schedule quota could be enforced. Confidence: 0.85
- A class schedule quota (kuota) of 0 means the admin has CLOSED registration for that schedule — it must NOT be treated as "unlimited". The backend (PendaftaranController@store) must reject any registration attempt when `kuota <= 0` with an auto-created rejected record + clear note (e.g., 'Kuota kelas belum dibuka (0).') and an error message to the member ("Maaf, kuota kelas ini belum dibuka..."), mirroring the full-quota rejection path. The user explicitly stated that when admin sets kuota to 0, nobody should be able to register. Confidence: 0.9
- A member must be allowed to register for MULTIPLE class types (jenis) within the SAME program — the backend duplicate-registration check must be scoped per (program, jenis), NOT just per program. The original `PendaftaranController@store` check (`where('program')` only) wrongly blocked a member who registered "tentative" from also registering "tematik" in the same program (rejected with "Kamu sudah terdaftar di program ini"), even though the UI presented both as selectable. Fix: add `where('jenis', $validated['jenis'])` so registering a different jenis is allowed while re-registering the same jenis is still blocked, and make the rejection message name the specific jenis. The "sudah terdaftar di semua kelas" state should trigger only when the member has registered for EVERY available jenis in that program. Confidence: 0.85
- Tematik vs Tentative class-type semantics (explicitly explained by the user): Tematik = per-week registration — materials and participants change every meeting, so members must re-register each week; an enrollment is only valid for the week it was made and auto-expires once that week's scheduled session has passed (the record is deleted so the "sudah terdaftar" state disappears from the dashboard and program listing, forcing re-registration). Tentative = once per semester — a single registration makes the member a member for the entire semester with no weekly re-registration, and the enrollment persists. Confidence: 0.9
- Member registration codes must follow the format `RB-DDMMYY-NNN` (e.g., `RB-310826-001`), where NNN is a GLOBALLY incrementing sequence that continues across days — it must NOT reset to 001 each day. The user explicitly corrected the per-day-reset interpretation ("jangan nomori member dengan urutan perhari nya... 001 itu berlanjut untuk hari hari berikutnya"): the sequence keeps counting up for members registered on subsequent days, and the date part reflects the member's registration date. Generate the code automatically at registration (dedupe against existing codes) AND backfill existing members via an artisan command so every member — new and existing — carries the code. Confidence: 0.9
