# admin-ui
- The admin panel navigation should be a fixed vertical sidebar on the LEFT side (Filament-style), not a horizontal top navbar — the user explicitly requested "navbar panel admin taruh di pinggir kiri juga agar seperti ui filament". The accepted pattern: dark sidebar with brand/logo + title at top, vertical nav items with icons and green active highlight, action buttons (Website/Logout) at the bottom, main content to the right of the sidebar; collapsing to a horizontal scrollable bar on mobile. Confidence: 0.85
- Consolidate related admin management sections (e.g., "Data Member" and "Pendaftar Program", or "Program" and "Jadwal Kelas") into a single navbar menu item to keep the sidebar clean and uncluttered — prefer inline/embedded management of child data within the parent page (expandable cards with inline add/edit/delete forms) rather than separate sub-pages or tab-separated views. Confidence: 0.90
- Use detail/show pages (click → detail view) for reviewing user documents and data rather than displaying everything inline in a table row. Confidence: 0.75
- Keep admin pages for similar data types (e.g., Data Member and Pendaftar Program) visually and functionally consistent — same layout style, same table features (export CSV), same header structure. Confidence: 0.75
- Avoid showing the same data redundantly across multiple admin pages (e.g., don't duplicate user documents in Pendaftar Program table since they're already visible in Data Member detail). Confidence: 0.70
- The admin panel should follow a dark monochrome terminal / Filament-style theme (including a left-side Filament-style sidebar — see the sidebar learning above) — black/gray/white palette (e.g., GitHub-dark-like `#0d1117` backgrounds, `#21262d` borders), and at most a single terminal-style accent color (e.g., green `#3fb950`) — the user explicitly requested "hitam abu putih seperti terminal command prompt ... simple native tidak warna warni seperti template ai". The admin look should feel like a native dev tool, NOT like a colorful AI-generated template. The terminal vibe must NOT make all text stiff: the user explicitly said the writing should not be too stiff ("tulisannya jangan terlalu kaku"), so body/content text (nav, stat numbers, labels, tables, buttons, forms) should use a modern readable sans-serif (Segoe UI / system-ui), with monospace (Cascadia/Consolas) reserved only for the terminal-style header/title accent (e.g., the "Panel Admin" title). Note: the user later asked to remove the green "> " prompt prefix from the "Panel Admin" title ("hapus tanda lebih dari di samping text 'panel admin'") — sidebar heading text should render plain, without terminal-style `::before` prompt prefixes. Confidence: 0.9
- Account-status badges in the admin UI (rejected/pending/approved) should be COLOR-CODED SOLID FILLED BLOCKS with a specific semantic mapping: rejected = solid red, pending = solid yellow, approved/confirmed = solid blue — implemented as fully-filled pills with white text and generous padding (e.g., rejected `#dc2626`, pending `#eab308`, approved `#1d4ed8`, all with white text and ~6px 14px padding), and applied consistently across every view showing that status (index list, kelola tab, detail/show). Thin pastel pills with a light background + 1px border are NOT acceptable — the user complained they render as just an unclear line/outline on the dark admin theme ("cuman line background aja sih?? gajelas banget") and explicitly asked for a solid "block warna" instead ("di block warna nya kalo rejected ya merah, pending kuning, approved biru"). This supersedes the earlier soft-pastel-pill preference and the even earlier monochrome-gray-pill preference for status badges. The user reiterated the exact mapping again ("pending ganti jd kuning dan approved biruu") when only rejected appeared colored, confirming they expect every distinct status to render with its own clearly-visible color, not just some. Fresh evidence: after the layout CSS override was found, the user again insisted "tetepp ga berubahhh warna nyaaa, yang pending blom kuninggg" — pending must visibly render yellow even on the dark admin theme, and any layout-level rule that neutralizes badge colors to monochrome must be removed. Confidence: 0.97
- Admin panels should be stripped of decorative flourishes (gradient orbs, floating/ornamental animations, heavy shadows, colorful inline styles, gradient card borders) for a flat, clean, "native" look — the "simple native, not AI-template" aesthetic applies to admin tools, in contrast to the public marketing pages where the user does want premium gradients/animations. Confidence: 0.78
- In-page sub-section selectors within an admin menu (e.g., Konten → "Edit Konten Profil" vs "Edit Berita"; Member → "Pendaftar Member" vs "Pendaftar Program") must be prominent, obviously-clickable buttons — solid filled backgrounds with icons, large padding, and a clear active state (solid green active vs dark-gray inactive, with title + subtitle) — never subtle underline tabs or plain-text links. The user explicitly complained the member tabs "ga mencolok, hamper mirip seperti text biasa" and that they made it confusing to find pendaftar member vs pendaftar program; the accepted pattern is the big switch/card buttons used on the Konten page (solid green active state, icon + title + subtitle) and the solid segmented buttons on the Member page. Confidence: 0.9
- After create/update/delete actions inside a tabbed admin page, the redirect must return to the SAME tab/section the user was working in (e.g., after adding/editing/deleting berita, redirect to `admin.konten.index?tab=berita`), not bounce back to the page's default tab — the user explicitly requested "setelah tambah berita, edit, dan hapus jangan langsung refresh dan Kembali ke page edit konten profil... pas ke refresh tetep stay di page edit berita". Preserve the active tab via a query param on the redirect. Confidence: 0.85
- Admin data/report pages should present registrants grouped hierarchically by meaningful categories (class type Tematik/Tentative → mode Online/Offline → specific class) rather than one flat mixed table — the user explicitly asked to split the "Pendaftar Program" report this way ("pisahkan lagi antara yang memilih kelas tematik dan tentative... pisahkan lagi... online... offline... pisahkan juga... sesuai kelas nya masing masing") so data isn't "tercampur aduk" and the admin's reporting is clear and easy ("biar jelas dan admin juga enak laporan nya"). Group per class into its own card with class info (day/time/pengajar) + quota count + member table. This nested-folder structure (📁 Jenis → 📁 Mode → 📁 Kelas) must be applied on EVERY admin page/tab that lists registrant data, not just dedicated report pages — fresh evidence: when the "Pendaftar Program" tab under Member → Kelola Member still showed a flat table, the user re-explained the full folder hierarchy ("di dalam pendaftar program itu ada 2 folder kelas tentative dan kelas tematik... masing masing ada 2 folder lagi online dan offline... ada folder jenis jenis kelas") and reiterated the purpose that admins can easily review reports and incoming data without it being mixed up ("biar gak campur aduk jadi satu"). Confidence: 0.9
- Admin menu/listing pages should expose a direct "Tambah" (add-new) action as a prominent button on the page itself (e.g., green "+ Tambah Program" in the header of Program & Jadwal, plus a "Tambah Program Kelas" button in the empty state), so admins can create new entries — like additional language class programs — without having to discover the create form via an "Edit" link on an existing card. The user explicitly requested an add-program feature reachable straight from the "Program & Jadwal" admin menu ("tambahkan fitur tambah program kelas agar admin bisa menambah jenis program kelas bahasa lain"), i.e., create actions should not be hidden behind edit flows. Confidence: 0.7
- Admin report/list pages with potentially large data volumes should NOT render the entire nested hierarchy (Jenis → Mode → Kelas) in one long combined view; instead use step-by-step drill-down navigation — step 1: choose class type via two large card-buttons (Kelas Tematik / Kelas Tentative with icon + explanation + registrant-count badge); step 2: choose mode (Online/Offline cards, only modes that have registrants); step 3: view per-class cards with the member tables. Each step offers a "←" back link to the previous step, and reopening the tab resets to step 1. The user explicitly requested this after seeing the grouped-all-in-one design: "kalau dibuat jangan jadi satu tampilan gitu gimana? biar ga bingungin admin ui dan css nya ... nanti kalo program kelas nya banyak dan pendaftar nya banyak sama aja bakal bingungin admin nya karena ga rapi" — a single-view layout is only fine for small datasets. Confidence: 0.85
- Admin tables — including tables generated dynamically in JS for the drill-down views — must reuse the layout's existing `.data-table` + `.table-wrap` CSS classes instead of hand-built inline-styled `<table>` markup. The user complained the inline-styled table rendered messy with fonts overflowing the column lines ("css table data pendaftar program berantakan ... font dll nya melebihi garis tabel"); the fix was switching to the shared classes plus `word-break:break-word` on long values (email) and `white-space:nowrap` on phone/timestamp cells so content stays inside the columns. Confidence: 0.85
- The admin dashboard's "recent registrants" box (titled "Member Terbaru") must display newly registered member ACCOUNTS — `User::where('role','member')->latest()` with name, email, signup date (WIB), and account-status badge — NOT program enrollment records (`Pendaftaran`). The user explicitly corrected this logic: "mau ku tuh di container itu yang muncul data orang yang baru aja daftar member bukan kok member yang daftar program" — i.e., "member who just signed up" means new account signups, not "members who registered for a program." The box's "Lihat Semua →" link accordingly points to Kelola Member, not the program registrant list. Confidence: 0.7
- Admin rejection actions must require a note/reason: the catatan field is REQUIRED when the admin sets status to rejected ("buat kolom catatan menjadi wajib kalau admin rejected, kalau approved opsional kolom catatanya") and stays optional (nullable) for approved/pending. Enforced in BOTH layers: backend validation (`required|max:1000` when status==='rejected' with a custom Indonesian error message, `nullable|max:1000` otherwise) AND frontend (label text switches to "(wajib jika ditolak)" in red with the textarea getting the `required` attribute dynamically on status change, plus inline error under the field). Confidence: 0.7
